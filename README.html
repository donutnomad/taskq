TaskQ — 分布式任务队列

Temporal 风格的 Go 分布式任务队列：多分区、at-least-once 投递、一致性哈希路由、dbleader 分区独占与长轮询消费。

README.md 2026-07-23 ~19 分钟阅读

概览与核心特性

TaskQ 是一个 Temporal 风格的分布式任务队列系统，使用 Go 实现。支持多分区、at-least-once 投递语义、一致性哈希路由、dbleader 分区独占、长轮询消费和可见性超时自动重投递。

特性说明
多分区队列水平扩展吞吐量，round-robin 分发写入
自动分区queue 按需自动创建；分区数纯 dynamic（DB 配置，全局默认 + per-queue override），运行时可安全增减
At-least-once 投递可见性超时 + 自动重投递（respool 换新 taskID），失败任务不丢，且不冻结 ackLevel
一致性哈希路由基于虚拟节点的哈希环，分区自动分配到集群节点
dbleader 锁 + RangeID CAS运行期开关由 dbleader 控制，写入围栏继续由 rangeID CAS 兜底
长轮询消费无任务时 worker 阻塞等待，任务到达即时唤醒
Sync Match写入时直接匹配等待中的消费者，零延迟投递
定向投递与原行 fallbackRoutingKey 在 deadline 前定向到指定 worker，过期后由同一 TaskID 参与普通消费

Frontend 是 SDK，不是独立服务

「四层架构」描述的是代码分层，不是部署单元。整套系统真正独立部署的进程只有 Matching。frontend.New() 在 Worker 进程内构造对象、不监听任何端口：round-robin 选分区和哈希环 Lookup(queue/pid) 全在 Worker 本地内存算完，再由自带的 gRPC 连接池直接拨号到 Matching 节点。它依赖的 ResolverProvider 同样是同进程内的 observer-only membership.Monitor，自行轮询成员表。

matching.Config.Store 使用显式的 matching.Store 契约，组合 queue.Store 与 dbleader.LockStore。连接生命周期由调用者管理；Matching.Stop 只停止服务自身。Store.Membership() 返回共享同一 GORM 连接的 membership.MemberStore 适配器，连接由父 Store.Close() 统一释放。

PhysicalQueue — 单分区核心

每个 PhysicalQueue 管理一个分区的内存状态和对外服务逻辑。它本身不再在构造时自动启动后台循环；writer、GC、可见性扫描都由外层单独运行。

当前生产路径为每个分区创建一个 dbleader LeaderTask。LeaderTask 获得锁后创建 PhysicalQueue，等待 writer 就绪，再并行运行 writer、GC ticker 和 visibility ticker；任一循环返回错误会取消另外两个循环并关闭该分区。

组件职责周期
taskWriter收集入队请求，批量 flush 到 DB，触发 sync matchLeaderTask 持锁期间持续运行
taskRuntime负责取任务、dispatch、ack/nack，把存储操作和内存状态衔接起来—
deliveryState内存中维护 outstanding/redelivery/acked 集合，追踪 ackLevel/maxReadLevel—
waiterRegistry管理长轮询阶段注册的等待者—
taskGC根据 ackLevel 删除已确认的任务，通过 CAS 持久化 ackLevelLeaderTask 内每 5s 执行一次
visibilityScanner检测超时的已分发任务，移入 redelivery 队列LeaderTask 内每 1s 执行一次

分区分配不在 queue 包内

membership 负责一致性哈希，把 queue/partition 映射到节点；matching 负责按需加载对应分区，并通过 dbleader.Manager 持锁运行、失锁停止；PhysicalQueue 只负责自己这一个分区的任务生命周期与长轮询。

Matching 包

gRPC 分区管理服务，每个节点只处理哈希环分配给自己的分区。gRPC 接口定义在 matching.proto：

RPC功能
AddTask写入任务到指定分区
PollTask消费任务（支持非阻塞和长轮询）
PollQueue一次轮询同一 owner 的多个分区，返回一个任务并回收同时命中的其他 lease
AckTask确认消费完成
NackTask拒绝消费，触发重投递（respool）；undelivered=true 表示仅归还未交付的 lease，不计入 attempt
GetQueueInfo查询队列的分区数

PartitionManager 核心逻辑

  • isOwner(queue, pid) — 通过哈希环判断本节点是否拥有该分区
  • getOrLoadPartition — 延迟加载，首次请求时启动 dbleader.Manager，等分区真正可服务后再返回
  • reconcile() — 成员变更时重新计算分区分配，加载新分区、卸载失去的分区

Frontend 包

客户端路由 SDK（不是独立服务、不监听端口），直接链接进 worker 进程，worker 通过它透明访问分布式队列。

  • 通过 GetQueueInfo 自动发现分区数量
  • round-robin 选分区写入
  • 快速扫描 + 长轮询消费
  • gRPC 连接池，成员离开时自动清理
  • 失败重试（FailedPrecondition / Unavailable）

Enqueue 流程

At-least-once 与业务幂等契约

Frontend.Enqueue 对可重试的 AddTask 路由或 gRPC 错误最多尝试 3 次，重试间隔为 50ms。Matching 可能已经提交任务，而 AddTask 响应在网络中丢失；后续重试会写入另一条任务。消费者进程退出、visibility timeout 和 Nack 也会触发重新投递。

1

生产者携带稳定幂等键

在 payload 中携带业务幂等键，例如 order_id + operation，应用层重试继续使用同一个键。

2

消费者在事务内写唯一记录

在业务数据库事务内写入幂等键唯一记录并执行副作用；唯一键冲突表示该任务已经处理。

3

事务提交后再 Ack

业务事务提交成功后调用 Ack。处理失败时返回错误或调用 Nack，让任务重新投递。

4

外部调用复用同一幂等键

外部系统调用使用同一个幂等键作为对方接口的 idempotency key，覆盖"外部调用成功、消费者提交前退出"的窗口。

CREATE UNIQUE INDEX uk_task_effect_idempotency_key
ON task_effects (idempotency_key);
要点

TaskQ 提供 at-least-once delivery；业务幂等键定义一次业务效果。两者共同构成端到端的 exactly-once 语义，缺一不可。

投递重试、respool 与 attempt 上限

失败任务（Nack、可见性超时）不再原地放回，而是 respool：以更高的 taskID 重写一条新任务，再确认（ack）老行。这样单条反复失败的任务不会永久钉死 ackLevel——acked 内存与 tasks 表持续 GC，队列始终能向前推进。该机制对齐 Temporal matching 层的 respoolTaskAfterError。

  • attempt 列 — tasks 表新增，记录该任务已失败的投递次数（首次写入为 0）。持久化在行上，进程重启 / 分区易主后计数不丢。
  • MaxAttempts（matching.Config） — 单任务的总投递次数上限。默认 0 表示不限次数：反复失败的任务持续 respool，ackLevel 不会被其阻塞，数据也不会被 TaskQ 主动删除。设为正数才启用上限，超过后任务被丢弃并仅记录一条 error 日志。
  • 毒丸处理 — 遇到无法处理的消息，推荐消费者自行持久化后回 Ack（而非 Nack），让任务正常出队。TaskQ 是运输层，不替业务决定丢弃数据，因此默认不设上限。

行为变化（自 respool 版本起）

Nack 返回后任务不再立即可 poll：新行由 writer 异步落库，需等下一轮 flush。同分区消费顺序进一步弱化：respool 把重试任务排到队尾（新 taskID）。老 attempt 的 token 在其 delivery 退役后，Ack/Nack 返回从 ErrStaleToken 变为 ErrTaskNotOutstanding。

运行时调整分区数

分区数是纯 dynamic 的（DB partition_config 表：_default_ 全局默认行 + per-queue override 行），queue 按需自动创建，无需预先声明。唯一安全的调整入口是 matching.Server.ResizePartitions：

// 把 my-queue 的分区数调整为 8（扩容）或 2（缩容），期间不丢任务。
if err := matchingServer.ResizePartitions(ctx, "my-queue", 8); err != nil {
    log.Fatal(err)
}

分区数分裂为 num_read / num_write 两个值，不变式 1 <= write <= read：写只落在 [0, write)，读枚举 [0, read)，因此被写的分区一定在被读的集合内。

为什么缩容必须走 orchestrator，不能直接 SetPartitions 减 read

「停止写高位分区」是跨节点最终一致的——靠各节点配置缓存 TTL 过期传播；而「减 read」是一步到位的。若在还可能有滞后节点往高位分区写入时就减小 read，该分区立刻失去 owner：没人 poll、GC 也停摆 → 其中的任务永不被消费、静默丢失。静默期 + drain 确认就是把这个最终一致的过程收敛为全局事实之后再动 read。

全局默认只允许 grow

SetDefaultPartitions 有硬 guard：缩小全局默认等于对所有无 override 的 queue 做一次无 drain 的隐式缩容。确需缩小时，先给每个目标 queue 显式 SetPartitions 钉住旧值，逐个 ResizePartitions 缩容后再调默认。

drain 超时与安全中间态

drain 轮询有总超时（默认 2 分钟），超时返回包装 ErrPartitionDrainTimeout 的错误，并上报卡住的分区号、ack_level/next_task_id、最早未确认的 task_id。最常见原因是高位分区里有反复失败的 poison 任务：MaxAttempts=0（默认）不限投递次数，这类任务会持续 respool，把 ackLevel 永久钉住。处理方式是先定位该任务（消费者自行持久化后回 Ack，或设置 MaxAttempts 上限），再重试缩容。

要点

超时 / 取消 / DB 错误时，缩容停在 (read=旧值, write=target) —— 这是安全中间态：高位分区停写但仍被 own、仍可 poll/ack、GC 仍在跑，数据不会孤立，修复后直接重试即可。

迟到 Ack/Nack 与配置不可读

缩容完成后，指向已退役分区的 Ack/Nack 重试返回幂等成功而非 InvalidArgument——能推进到「减 read」就意味着该分区已确认完全排空，此类请求必然是重复的。另外，当分区配置读不到且无缓存时，matching 返回 Unavailable 拒绝服务（而非回退到默认值），避免把写入放行到已退役的分区。

PhysicalQueue 内部结构

deliveryState 状态

字段含义
ackLevel已确认的最高连续 taskID
readLevel已从 DB 读取的最高 taskID
maxReadLevelDB 中已知的最高 taskID
outstanding{taskID → 已分发但未确认的任务}
respooling{taskID → 正以新 taskID 重写、等待落库}
redelivery[waiter 消失等待原地重投递的任务]
acked{taskID → true}，已确认但 ackLevel 尚未推进

ackLevel 推进规则（advanceAckLevel）

从 ackLevel+1 开始逐个检查：在 outstanding 中 → 停止（还在处理中）；在 respooling 中 → 停止（新行未落库，绝不提前 ack 老行）；在 redelivery 中 → 停止（未重新确认，防止 GC 删除）；在 acked 中 → 推进并继续检查下一个；其他 → 停止（还没读到）。

deliveryState 只维护内存中的任务状态；真正和 DB 打交道的是 taskRuntime。这样状态规则和存储调用分开，PhysicalQueue 自己只需要装配这些组件。

快速开始

完整可运行示例（SQLite 单进程） 
package main

import (
    "context"
    "fmt"
    "log"
    "net"
    "net/netip"
    "time"

    "github.com/donutnomad/taskq/frontend"
    "github.com/donutnomad/taskq/matching"
    "github.com/donutnomad/taskq/membership"
    "github.com/donutnomad/taskq/store/gormstore"
    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
)

func main() {
    ctx := context.Background()

    // 1. 创建存储
    store, _ := gormstore.NewSQLite("taskq.db", gormstore.Config{AutoMigrate: true})
    defer store.Close()

    // 2. Membership 适配器与 queue/leader store 共享连接
    memberStore := store.Membership()

    // 3. 启动成员发现
    lis, _ := net.Listen("tcp", "127.0.0.1:0")
    addr := lis.Addr().String()
    addrPort, _ := netip.ParseAddrPort(addr)
    lis.Close()

    monitor := membership.NewMonitorWithConfig(membership.MonitorConfig{
        AdvertisedServices: []string{"matching"},
        WatchedServices:    []string{"matching"},
        Store:              memberStore,
        BroadcastAddr:      addrPort,
        PollInterval:       time.Second,
        PropagationTime:    time.Second,
        ReplicaPoints:      100,
    })
    monitor.Start()
    monitor.WaitUntilInitialized(ctx)
    defer monitor.Stop()

    // 4. 启动 Matching 服务
    srv, _ := matching.NewServer(matching.Config{
        Store:         store,
        Monitor:       monitor,
        ListenAddr:    addr,
        BroadcastAddr: addr,
        QueueConfigs:  map[string]int{"demo-queue": 4},
    })
    srv.Start()
    defer srv.Stop()

    // 5. 创建 Frontend
    fe, _ := frontend.New(frontend.Config{
        ResolverProvider: monitor,
        QueueName:        "demo-queue",
        DialOpts:         []grpc.DialOption{grpc.WithTransportCredentials(insecure.NewCredentials())},
        PollTimeout:      5 * time.Second,
    })
    defer fe.Close()

    // 6. 生产
    fe.Enqueue(ctx, []byte(`{"type":"send-email","to":"user@example.com"}`))

    // 7. 消费
    data, token, err := fe.Dequeue(ctx)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Printf("收到任务: %s\n", data)

    // 8. 确认（或 Nack 重投递）
    fe.Ack(ctx, token)
    // fe.Nack(ctx, token) // 拒绝，任务会被重新投递
}

可直接运行仓库里的完整示例：

go run ./internal/example/

上线顺序

先创建列与索引，再部署读写 routing 字段的 TaskQ 二进制。零值 deadline 持久化为 NULL，表示永久按 routing key 定向；非空 deadline 到期后由原任务行直接参与普通 poll，原任务行、TaskID 和 AckLevel 保持连续。每次 delivery 生成新的 token；旧 attempt token 无法 Ack 或 Nack 后续 delivery。

    AutoMigrate: false,

if err != nil {
    return err
}

monitor := membership.NewMonitorWithConfig(membership.MonitorConfig{
    AdvertisedServices: []string{"matching"},
    WatchedServices:    []string{"matching"},
    Store:              store.Membership(),
    BroadcastAddr:      netip.MustParseAddrPort(broadcastAddr),
    PollInterval:       3*time.Second,
    PropagationTime:    5*time.Second,
    ReplicaPoints:      200,
})
monitor.Start()
initCtx, cancelInit := context.WithTimeout(ctx, 30*time.Second)
defer cancelInit()
if err := monitor.WaitUntilInitialized(initCtx); err != nil {
    monitor.Stop()
    _ = store.Close()
    return err
}

server, err := matching.NewServer(matching.Config{
    Store:             store,
    Monitor:           monitor,
    ListenAddr:        listenAddr,
    BroadcastAddr:     broadcastAddr,
    QueueConfigs:      queueConfigs,
    ReconcileInterval: 5 * time.Second,
})
if err != nil {
    monitor.Stop()
    _ = store.Close()
    return err
}
if err := server.Start(); err != nil {
    monitor.Stop()
    _ = store.Close()
    return err
}

<-ctx.Done()

// Shutdown 顺序：停止流量与分区，再停止成员心跳，最后关闭共享 DB。
server.Stop()
monitor.Stop()
return store.Close()

每个进程创建一个父 gormstore.Store，Matching 与 Membership 共用该连接池。应用负责在 Store.Close() 前停止所有 Server、Monitor 和 Frontend 实例。AutoMigrate: true 适用于本地开发和测试。
